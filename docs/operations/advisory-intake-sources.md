# Advisory intake and source coverage

Reviewed November 24, 2026, Central time.

## What is live

OMG receives the CVE Program archive and deltas, Arch Linux Security Tracker, and CISA KEV through the advisory service. An intake completion sends an event to the public dashboard. The browser holds a WebSocket connection and hydrates the changed sections in place. Source check times and failure states remain visible.

The private enrichment Worker matches Google Project Zero and verified vendor disclosures against published CVE records in `omg_advisories` on PlanetScale. It stores evidence identity, vendor, product, dates, source references, first observation, and the matched archive revision hash. Public details can join that evidence with CISA KEV, available ENISA exploitation records, and the dated FIRST EPSS score.

Chrome Releases adds a separate direct publisher watch. The collector requests the desktop stable feed every minute, uses conditional HTTP requests, and stores vendor statements and receipt times independently of the canonical CVE archive. The dashboard lists recent exploitation reports directly from Chrome, with a pending label until the corresponding published CVE arrives. Documented zero-days have their own list.

## How to reduce and measure delay

Keep each feed's publication or revision timestamp, first observed timestamp, commit timestamp, source record ID, and content hash. Separate backfill records from observations measured after a connector starts, and preserve original source timing even when an alias or CVE is attached later. Keep source-specific withdrawals and revisions. Accept the earliest validated disclosure for triage and retain all evidence behind that call.

Measure publisher publication to first observation, observation to durable commit, commit to dashboard update, and cache age at install review. Track p50 and p95, source errors, backlog, matched identities, and added coverage. Compare only equivalent timestamp types and call out date-only data. Label an advisory pending when a vendor discloses an ID before the archive has that CVE. Keep the source report and compare dates after the match arrives.

Use a source's change notifications when available. Otherwise use a revision manifest or conditional requests, with overlap at the cursor, bounded bodies, jitter and backoff. High-frequency checks are useful for small, independently updated publisher feeds. Backfills and slower bulk enrichment should run separately from the fast path. The Chrome feed returned about 2.25 MB on a changed full request during the probe, so the conditional 304 is important.

## Human review for AI-assisted installs

OMG's existing consent implementation declines unattended approval for findings and unknown coverage. Generic `--yes` cannot accept advisory or coverage risk. The review binds the operation, versions, artifacts, policy, and caller. A change in those inputs requires another review. [OMG security policy and install review](https://github.com/omg-cli/omg/blob/main/docs/security.md#install-time-vulnerability-review)

A foreground terminal indicates how input was delivered. It does not independently authenticate a person. For agent-facing integrations, keep privileged install operations in a separate approval path. The local approval should display the exact resolved package and runtime versions and their evidence, request an OS or hardware user-verification gesture where supported, and produce a short-lived single-use receipt bound to that operation. Keep the credential and receipt issuance outside the agent's tool interface. The CLI should refuse unattended operations that require review and return a machine-readable reason for the user interface to display.

Use validated affected-version evidence and integrity policy for admission. Treat a vendor exploitation report, CISA listing, or a confirmed zero-day as urgency once it matches the requested artifact. Preserve lower-confidence signals for triage with links and timestamps. The user should see when exact applicability is still being established.

## PlanetScale and Cloudflare operations

The cluster hosts several logical databases, including Crowdrail, OMG advisories, OMG platform data, and Token Dashboard. The 24-hour Insights sample was dominated by Crowdrail message and identity writes. Advisory lookups and the recent list used their existing indexes. The former dashboard zero-day join fetched individual CVE bodies. The PlanetScale importer now matches a batch of identifiers with indexed lookups and avoids those payload transfers. Unchanged enrichment rows retain their original evidence timestamps.

The advisory writer and replica Hyperdrive configs have SQL result caching disabled. A live check found a five-minute-old API checkpoint while PostgreSQL had already committed the newer value. After updating the advisory replica config, the API returned the committed checkpoint. The dashboard still coalesces public reads in its Durable Object. This leaves freshness at the database copy that owns it and avoids multiplying database queries by the number of viewers.

Apply the numbered SQL migrations in [the CVE Worker SQL folder](../../workers/cve/sql/) to `omg_advisories` before deploying the enrichment Worker. Grant the advisory writer select, insert, and update on the new tables and grant the advisory replica reader select. The enrichment Worker uses the existing advisory writer binding. The dashboard calls it through a private service binding. Deploy the enrichment Worker before the public dashboard. Keep the advisory producer's `omg-cve` Tail Worker binding in its production configuration. A failed upstream check preserves the last confirmed rows and a stale indication.

For a shared-cluster performance pass, capture a comparable longer window for the Crowdrail writers, cache hit rates and waits. Follow the hot query to its owning service before changing trigger behavior or batching. The reviewed advisory changes address read freshness and repeated transfers. They do not establish a cluster-wide speedup.
