# omg-web code audit — 2026-11-11

This report preserves findings at the original baseline. The implementation status below records the subsequent changes on `codex/docs-audit-upgrade`.

Read-only, scoped correctness and maintainability review of the website, documentation delivery and selected API boundaries. This is not an exhaustive codebase or security audit. Baseline supplied by parent: clean `main`, commit `42eea87`. I observed a clean working tree before analysis. No dependencies installed, no full build/test suite run, no Git changes or external mutations. Existing generated output was inspected and is supporting evidence only; its source provenance was not regenerated in this audit.

## Prioritized findings

### P2 — Prerendered staging pages bypass the stage robots policy

**Source location:** `site/worker.js:5`–8 (outer Worker response is returned undecorated); `site/src/hooks.server.ts:52`–53 (decoration exists only inside SvelteKit); `site/src/lib/server/public-files.ts:69`–70 (non-production noindex implementation). `site/_headers:1`–8 contains no stage robots rule.

**Trigger:** GET or HEAD `/docs/installation/` or any prerendered `/docs/`, `/runtimes/`, `/guides/`, `/compare/` page on a staging deployment.

**Evidence:** The adapter's generated `_worker.js:93`–99 handles prerendered pages through `env.ASSETS.fetch(req)`, bypassing `server.respond` and therefore the Svelte hook. This is also implemented in installed `@alchemy.run/frontend-frameworks/src/sveltekit/WorkerShim.ts`. Existing generated docs HTML explicitly contains `meta name="robots" content="index, follow, max-image-preview:large"`; generated `_headers` only applies noindex under `/_app/*`. Site staging and production point to the same built asset directory. The outer wrapper does not compensate for this bypass.

**Minimal isolated reproduction run:** Evaluated the existing generated shim with an in-memory cache and ASSETS response under `DEPLOYMENT_STAGE=staging`; GET `/docs/installation/` returned 200, called `server.respond` zero times, and retained no X-Robots-Tag. No server or network was used. Result:

```json
{
  "stage": "staging",
  "appCalls": 0,
  "status": 200,
  "robotsHeader": null,
  "cacheControl": null,
  "body": "<meta name=\"robots\" content=\"index, follow\">"
}
```

The fake ASSETS body demonstrates the control-flow bypass; the real generated HTML/meta and `_headers` inspection independently establish that the adapter has no stage noindex policy to apply.

**Impact:** Public staging documentation can be indexed despite the code's stated non-production indexing policy. The same boundary means the custom `withPublicHtmlCache` policy is not applied by the hook to prerendered docs on a direct production request either; actual asset defaults determine their cache policy.

**Minimal fix:** Apply stage-dependent response decoration at the outer `site/worker.js` boundary after `headSafeFetch`, covering generated cache hits, ASSETS and dynamic responses. Preserve Svelte's rendered CSP; avoid blindly replacing the asset CSP. If moving shared headers to the outer boundary, remove duplicate responsibilities from the hook where appropriate. Test built adapter GET and HEAD responses for a docs page under prod and staging, including cache hits. Existing tests only exercise `withSiteHeaders` directly and local Vite routes, which cannot catch this boundary.

### P2 — Edge security-feed refreshes are not coalesced

**Source location:** `site/src/lib/server/security-updates.server.ts:117`–134, and `:142` (runtime path bypasses the `pending` guard at `:144`).

**Trigger:** Multiple requests encounter a cold or expired feed cache before the first background refresh finishes. GET `/security/feed.json` is public; `/security/` also loads it.

**Evidence:** Every edge request independently registers `refresh(fetcher, previous)` before any refresh result has been stored. Each refresh calls both GitHub repository APIs. The module's single-flight promise is used only when the edge runtime is absent.

**Minimal isolated reproduction run:** Transpiled the actual TypeScript module to CommonJS in memory using the already-installed TypeScript compiler, loaded its actual schemas and snapshot, and invoked `securityFeed` ten times concurrently with one empty in-memory cache and a deferred fake GitHub response. No files or network were changed. Output:

```json
{
  "concurrentColdCacheRequests": 10,
  "githubFetchesBeforeCompletion": 20,
  "queuedRefreshTasks": 10,
  "returnedStale": true
}
```

**Impact:** Traffic bursts multiply external API requests precisely during cold starts, cache expiry or cache failure. Upstream throttling keeps the public feed stale; concurrent refresh completion can also overwrite a newer cached feed with the snapshot held by an older refresh. No private data exposure is asserted.

**Minimal fix:** Coalesce background refreshes per cache origin/key within an isolate. Retain immediate stale responses and clear the promise after success/failure. Origin-keyed pending work is needed because the existing tests deliberately isolate origins. For cross-isolate coordination, a scheduled refresh or durable coordinator is a larger alternative; a module map alone only bounds duplication within an isolate. Add a focused concurrent cold/expired-cache test; existing edge tests cover cache reloads, failures and expiry sequentially.

### P2 — Deployment success does not prove documentation freshness at the edge

**Source location:** `site/package.json:19` (`build:check && wrangler deploy ...` has no edge invalidation or old-asset verification step); `site/src/lib/server/public-files.ts:14`–15 (shared cache allowance); generated adapter cache keys are the request URL with no deployment identity (`site/node_modules/@alchemy.run/frontend-frameworks/src/sveltekit/WorkerShim.ts:136`–150).

**Observed live evidence supplied by parent:** A successful Wrangler deployment and new `/health` version were followed by root HTML returning a Cloudflare cache HIT with the old page for roughly ten minutes; a targeted purge was required. I did not independently repeat the deploy or purge. Deployment operations remain owned by parent.

**Impact:** A docs/release correction can be deployed yet readers and verification requests still receive old HTML. `/health` proves Worker code version, not freshness of a separately cached HTML response. A full docs framework migration would inherit this issue unless deployment/cache behavior is handled.

**Minimal fix:** Document an explicit post-deploy validation of corrected public pages, and make cache invalidation/versioning concrete in the release path. Choose targeted known-URL purge or deployment-version cache keys; be explicit about the different Cloudflare cache layers and scope. Do not promise that a zone CDN purge automatically clears every adapter Cache API entry without verifying the chosen mechanism. Test/report both deployed Worker version and changed rendered content. This is an operational reliability finding, not a claim that a ten-minute cache TTL is inherently wrong.

### P2 documentation-maintenance gap — Default freshness gate does not verify upstream references

**Source location:** `site/package.json:17` invokes `check-docs-freshness.mjs` without `--clone`; `site/tools/check-docs-freshness.mjs:306`–308 runs upstream verification only with that explicit option. `site/src/lib/docs/topics.ts:21`–22 pins all eight topics to one commit/date. `docs/operations/seo-plan.md:95`–97 overstates what the optional checker proves.

**Observed commands:**

- From `site/`, `node tools/check-docs-freshness.mjs` passes: `8 registry topics validated`.
- From `site/`, `node tools/check-docs-freshness.mjs --clone ../../omg --revision HEAD` fails all eight topics because `c43c8ff10701be2cf6a17a39d030fd7180db9308` does not exist in the local upstream clone.
- Sibling `omg` clone is non-shallow, its origin is `https://github.com/omg-cli/omg.git`, and its current HEAD was `fd3ca5ad0b2def1ae328abb4cb448befebe82412`.

**Limit:** Missing in this local clone is not proof that the public GitHub commit URL is unavailable. No fetch or remote history check was performed.

Even with a usable pin, optional verification checks only the single declared `docs/<topic>.md` path (`check-docs-freshness.mjs:246`–253). It does not require selected upstream revision to equal reviewed commit, contrary to the operations document, and does not detect CLI implementation changes with unchanged Markdown. The topic footer explicitly says CLI code and docs were checked at the pinned commit, so advancing the pin still needs substantive human review.

**Impact:** The named freshness check and normal CI can remain green while reference provenance is unavailable locally or upstream behavior changes. This is distinct from content rendering correctness.

**Minimal fix:** Describe default check as inventory/provenance-shape validation. Add a deliberate cross-repository review command/check using an available immutable upstream revision, align operational docs with its true scope, and store source/dependency evidence for content that relies on CLI code. Do not simply advance the pin to make the check pass. Keep offline CI separate from intentional upstream-drift review if external availability would make routine CI flaky.

## Architecture map

- `site/`: SvelteKit 3 / Svelte 5 app built by Vite, Cloudflare adapter supplied by Alchemy. `site/worker.js` wraps generated Worker to turn HEAD into GET and strip response bodies, avoiding Cache API HEAD constraints. Wrangler configs independently deploy production/staging with D1 + licensing service binding.
- `site/src/routes/docs/+layout.ts`: prerenders the docs subtree. Eight one-file routes import eight typed TS content modules. `docs/topic.ts` defines a closed block union; shared Svelte block/diagram components render escaped strings. `topics.ts` owns sidebar, index, sitemap and provenance metadata.
- Learning pages (`/runtimes/`, `/guides/`, `/compare/`): separate catalog, dynamic imports keyed by slug, same block model plus sources/related links, prerendered through server loaders. A separate Markdown serializer feeds `/markdown/[category]/[slug]/`.
- `/llms.txt`: dynamic plain-text index of learning Markdown and docs HTML. It has correct explicit MIME/noindex/content-signal headers. Handbook docs currently have no equivalent Markdown endpoint; no `llms-full.txt` exists. This is a capability gap, not an existing broken route.
- `SeoHead.svelte` plus `shared/public-site.ts`: canonical origin, OG/Twitter and JSON-LD serialization. Sitemap uses topic reviewed dates and learning modified dates; structured data escapes script breakouts. Per-page SEO tests already exist.
- Documentation navigation: topic sidebar, breadcrumbs and stable section IDs exist. Topic pages have no local section TOC, search, prev/next links or code-copy control. These are product enhancements, not correctness bugs. Index page has an on-this-page TOC.
- `hooks.server.ts`: Better Auth request handling, block direct organization plugin routes, POST auth mutation limiter, stage/security headers and public HTML cache helper. Prerendered assets bypass this hook in deployment.
- Authenticated site routes load provider sessions and call typed service-boundary modules. Licensing Worker gets explicit service-binding authentication plus BFF secret/session role, and operator routes have separate admin gates. Private route prefixes are excluded from shared HTML caching. Selected paths have malformed-input/body-limit/authorization tests.
- `workers/api/`: independently deployed API with shared route registry and contract parsing, D1, auth/session/token hashing, licensing, billing/Stripe inbox and reconciliation, privacy, telemetry, analytics, administration, scheduled retention/health jobs. Uniform private response headers and response security decoration. I sampled the dispatcher, boundary helpers and tests; I did not read every handler in depth.
- `shared/`: cross-runtime route/contracts and domain models avoid duplicating site/API protocol assumptions. Effect major versions intentionally differ (site 4, API/root 3); this is a maintenance cost to document, not evidence of an interoperability defect.

## Existing verification and limits

Reviewed tests include handbook shape/provenance/command guards, renderer escaping and diagrams, learning Markdown export/invalid-slug boundaries, public metadata/sitemap/security/cache helpers, HEAD wrapper, security-feed sequential caching/failure behavior, route/auth/session/admin contract tests, and Playwright public discovery/no-JS/mobile navigation coverage.

CI's public browser job (`.github/workflows/ci.yml`) runs Vite `dev:e2e`, not the built Cloudflare Worker. It therefore does not cover adapter ASSETS bypass, deployed Cache API behavior or real bindings. Authenticated Playwright specs require `E2E_BASE_URL`; the standard public CI job does not run those bound deployment scenarios. Dry-run deployment checks can prove bundling/config compatibility without proving deployed headers/content freshness.

The audit ran two small in-memory reproductions and the read-only freshness commands above, not the full tests/build. There is no new claim that the existing suite passes. No confirmed account/admin authorization bypass or private response cache leak was found in the sampled paths; that is not a whole-system security guarantee.

## Maintainability recommendations for the documentation work

1. Preserve routes/canonical URLs, auth/BFF boundaries and API isolation through the docs improvement; avoid a framework migration solely to gain navigation and search.
2. Author content once and derive HTML, Markdown/agent representations, navigation and sitemap from the same model. Current typed blocks already give safe HTML and diagram semantics; they make rich inline prose/links and author contribution cumbersome.
3. If adopting Markdown/MDX, define one safe content boundary and a link/inventory check, and preserve diagrams and version/source provenance. TypeScript content tables currently disallow prose links by test, which is a deliberate format limitation rather than a parser defect.
4. Distinguish latest release guidance from source-head guidance at page and command level. The index mentions that main differs from the latest release; readers need actionable applicability on each affected topic.
5. Close deployed-boundary coverage before expanding docs: stage robots and response cache policy must hold for both generated and dynamic pages; a healthy Worker must not be confused with fresh public HTML.

## Implementation status

- **Staging robots bypass fixed:** the outer Worker now applies stage robots policy after adapter assets/cache responses. GET/HEAD regressions preserve CSP, production headers and the XML sitemap exception.
- **Feed refresh duplication fixed within an isolate:** concurrent refreshes share a promise per cache origin/key, released after success or failure. Cross-isolate coordination remains outside this change.
- **Source maintenance fixed:** normal CI validates the recorded release inventory offline; an explicit clone/revision check verifies immutable bytes and reports affected pages on implementation or Markdown drift. The record never advances review dates by itself.
- **Agent/reader gaps addressed:** one catalog covers 43 public documents, including 18 new SveltePress Markdown guides. All have Markdown exports and appear in the manifest, search and llms indexes. Native Markdown preserves OMG's layouts and CSP; no second docs application is deployed.
- **Search cache regression prevented:** explicit `no-store` and `private` response policies survive the public HTML cache helper. Search terms/results do not receive shared HTML cache policy.
- **Edge freshness remains a release verification responsibility:** deploying Worker code is not proof of fresh cached HTML. Follow the content checks in documentation maintenance after publication; this branch has not been deployed.

The website changes have unit and browser verification. Provider downloads, every CLI backend and authenticated deployed flows were not executed by this audit. The final branch validation receipt belongs in the implementation plan.
